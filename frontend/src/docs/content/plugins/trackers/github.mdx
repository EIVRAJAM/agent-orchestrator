---
title: GitHub issue intake
description: Opt-in, assignee-scoped worker creation from GitHub issues.
---

This guide uses the GitHub tracker and your existing GitHub authentication. GitLab is also supported. Follow [GitLab authentication](/plugins/scm) and use the provider selection described below.

## Configure intake

Intake needs two opt-ins, and both default to off: enable it on the daemon and configure a project with an assignee filter. Each matching issue can start a worker session, so use the filter to limit which issues Orchestrator handles.

For the desktop app, add `AO_TRACKER_INTAKE=on` to the environment your login shell exports, such as `~/.zshrc`, then relaunch Orchestrator. The app passes that environment to its daemon. For a standalone daemon, set the variable in its launch environment and restart it.

Then configure the project. `ao project set-config` replaces the full project config, so read the [full-config warning](/configuration/projects#update-from-the-cli) before using it.

```bash
ao project set-config my-app \
  --tracker-intake \
  --tracker-repo owner/repo \
  --tracker-assignee alice
```

When `trackerIntake.provider` is omitted, Orchestrator infers the provider from the project's Git remote. GitHub hosts select `github`; other remote hosts select `gitlab`. An empty or unparseable remote falls back to `github`. When the repository is omitted, Orchestrator can also derive it from that remote.

For an explicit GitLab intake configuration, set `trackerIntake.provider` to `gitlab` in the full configuration object through the daemon API. The CLI has no `--tracker-provider` flag on `project set-config`; that flag belongs to `spawn`. If you use `--config-json`, preserve all other project settings and heed the effort-loss warning above. The intake portion of the object is:

```json
{
  "trackerIntake": {
    "enabled": true,
    "provider": "gitlab",
    "repo": "group/project",
    "assignee": "alice"
  }
}
```

This is a fragment to merge into the full configuration, not a replacement for it. Use `ao project get my-app --json` to inspect the stored configuration, keeping in mind that its output omits effort.

If `AO_TRACKER_INTAKE` is unset, the project config is still stored and validated, but no sessions are spawned. The daemon logs a warning at startup naming how many projects have intake configured while the flag is off.

For one GitLab issue without enabling intake, use `ao spawn --project my-app --name issue-42 --tracker-provider gitlab --issue 42`.

## Optional PR-ready comment

Write-back is a separate per-project opt-in and is disabled by default. When it is enabled, Orchestrator posts at most one short deterministic comment containing the PR link after the session's PR is ready for review and its CI is green:

```bash
ao project set-config my-app --tracker-writeback
```

The equivalent full-config fragment is:

```json
{
  "trackerWriteback": {
    "enabled": true
  }
}
```

This does not close or transition issues, change labels/assignees/milestones, or merge anything. Only the PR URL is written; issue titles, bodies, comments, prompts, and agent output are never echoed. Delivery uses the tracker authentication already configured for intake.

AO records a durable intent keyed by project, canonical issue ID, and PR URL. Repeated observations or restarts cannot enqueue a second comment. If a provider response is lost after the request, the row is marked `uncertain` and is deliberately not retried: at-most-once is safer than risking a duplicate comment. A project opt-in does not guarantee a comment if the tracker token lacks comment scope; that failure remains visible in the write-back state and logs without exposing tokens or issue content.

## Current boundary

Matching issues may create sessions and provide issue context. Intake itself remains read-only. The optional write-back above is the only tracker mutation; it does not assign workflow states or close issues. PR and CI observation belongs to Orchestrator's separate [source-control capability](/plugins/scm).
